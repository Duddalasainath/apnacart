Pretext.js: text layout that never touches the DOM

Measuring text height in the browser is slower than it should be. Pretext.js uses Canvas measureText once, caches the widths, and computes everything else in pure math. No reflows. Around 1,000 blocks in 2ms.

At some point building a chat UI or a virtual list, you hit this: the browser slows down every time you ask it how tall a text block is. It doesn't matter if you batch things carefully. Reading offsetHeight or getBoundingClientRect() forces the browser to flush its layout queue right there, synchronously. Do that for hundreds of elements and your frame rate is gone.

Pretext.js sidesteps this completely. It measures text using Canvas measureText() which never triggers a reflow, caches the glyph widths, and then figures out line counts and heights through pure math. After the first call, there are zero DOM reads.

Why offsetHeight is a trap

The browser builds a layout tree but delays the actual geometry calculation until something asks for it. The moment you read offsetHeight, it calculates everything. If you just wrote to the DOM before that read, it has to recalculate from scratch. Do this in a loop and you get what Chrome DevTools calls layout thrashing. 

// this causes a reflow on every single iteration
items.forEach(item => {
  const div = document.createElement('div');
  div.textContent = item.text;
  container.appendChild(div);
  heights.push(div.offsetHeight); // reflow here, every time
});

The general advice is to batch reads before writes. Pretext.js goes further and removes the read entirely for text height calculations.

How it works

Two functions is really all you need. prepare(text, font) runs the text through Canvas measureText() once per unique glyph and stores the widths. layout(prepared, maxWidth, lineHeight) walks those cached widths and breaks lines using arithmetic, no DOM involved. Call prepare once, call layout as many times as you want at different widths without re-measuring anything. 

import { prepare, layout } from '@chenglou/pretext';

const handle = prepare('Hello, world!', '16px "Inter"');

// works at any container width, no reflow
const { height, lineCount } = layout(handle, 320, 24);

console.log(height);     // 24 (one line at 24px line height)
console.log(lineCount);  // 1

The benchmark is around 1,000 text blocks in 2ms. For most UIs that kind of headroom makes height pre-computation on mount actually practical.

Installing

npm install @chenglou/pretext
# or pnpm add / bun add

No bundler needed if you want to try it fast. Just use the ESM build directly: 

<script type="module">
  import { prepare, layout }
    from 'https://unpkg.com/@chenglou/pretext@0.0.3/dist/layout.js';
</script>

The centering calculation looks like this. Pretext gives the exact text height so no DOM read is needed: 

const handle  = prepare('P', `900 ${fontSize}px Arial Black`);
const { height } = layout(handle, canvasWidth, fontSize * 1.2);

const offsetY = (canvasHeight - height) / 2;

Where it actually helps

For a regular content page you genuinely don't need this. But there are a few situations where it makes a real difference.

Virtual scroll is the obvious one. To know which items are in the viewport you need the height of every row, including the ones that aren't rendered yet. With Pretext you can compute all row heights upfront without putting a single element in the DOM. 

const rowHeights = messages.map(msg => {
  const h = prepare(msg.text, '15px "Inter"');
  return layout(h, 560, 22).height + 24;
});

LLM streaming is the other case I keep running into. When tokens are arriving fast and every token changes the bubble height, triggering reflow on each update is too slow. Pretext handles resize in under a millisecond so you can update the layout on every token without dropping frames.

Canvas editors are the third one. If you are building anything Figma-style where text renders to canvas, you need exact line positions for cursor placement and selection. The walkLineRanges API hands you line geometry without allocating intermediate strings, which keeps GC pauses out of the picture.

The API in one place

prepare(text, font) — measure and cache. Call this once per piece of text.
layout(handle, maxWidth, lineHeight) — returns { height, lineCount }. Fast, no DOM.
layoutWithLines(handle, maxWidth, lineHeight) — same but also returns line objects with text and widths.
walkLineRanges(handle, maxWidth, cb) — iterate lines without allocating strings.
layoutNextLine(handle, start, maxWidth) — step through one line at a time.
clearCache() — free internal caches when you no longer need them.
setLocale(locale) — controls word breaking for CJK, Arabic, etc.

Worth trying?

It is a small library with zero dependencies and full TypeScript types. If you are not hitting the reflow problem it will not do anything for you. But if you are building something that measures a lot of text, especially dynamically, it is worth dropping in. The prepare and layout calls are simple enough that you can integrate it in ten minutes and immediately see whether it helps.

If you are building a virtual list, an AI chat UI, or any Canvas-based renderer that needs reliable text geometry, it is worth adding to your toolbox. The prepare + layoutWithLines pattern alone covers 90% of use cases in a handful of lines.
